白天给产品写功能，晚上给 agent 派活。这两件事的共同点是：最后都得有人签字。

主力在后端和基础设施，最常干的活是把一条红着的流水线救回来。不写框架、不追新语法，偏好能跑、能测、能复现的东西。判断标准只有一条——这活能不能被验收。

此刻：在给一个跑了很久的仓库做减法·上海

看我在修什么 GitHub

现在

三件事同时在跑，都不是新项目。

  1. 仓库做减法能删的依赖删掉，能交给机器的交给机器。跑了很久的仓库最容易长出一身没人敢动的配置。
  2. 把 agent 塞进日常读日志、翻上游 issue、开浏览器点一遍界面；我只负责判断和签字。
  3. 写排障笔记每次翻车都留一条能复现的路径，下次不用从零开始猜。

干过的几件小事

共同点：报错信息都在说谎，或者说了一半真话。

一条天天红的 CI

上游把 API Key 降级成只写，读取统计必须换 OAuth。Key 本身没坏，写还照常写，只有读被拦——所以报错里那句 "only for plugins" 是唯一线索。

处理没换 Key 重试，而是加了道凭证预检：跑前先探一次，探不通直接给人话。

结果两分钟的 Python traceback 变成五秒的中文提示。

一个返 202 的接口

不是没数据，是统计还在算。上游用 202 表示「已接受、稍后给你」，客户端把它当成了空结果。

处理改成轮询等待，最多十二次，每次十秒。

结果周报再没出现过半空的表格。

一个只能靠人点鼠标改的配置

平台没有 API，只有后台表单。每次改都要人肉登录、找菜单、填字段，还容易点错。

处理交给 agent 按固定路径点，点完回读页面校验一遍。

结果省下的时间拿去写测试，这才是它该待的地方。

我怎么和 agent 分工

它不是我的助手，是我雇的一个不用睡觉的侦察兵。判断权始终在我这边。

  1. 1

    我提目标

    要解决什么、验收标准是什么，先说清楚。说不清就先别派活。

  2. 2

    它去侦察

    读日志、翻上游 issue 和 changelog、开浏览器把界面点一遍，把原始输出带回来。

  3. 3

    它给证据，不是给结论

    「我觉得是权限问题」没用。要么有那一行报错，要么有那个响应头。

  4. 4

    我判断、签字

    改什么、不改什么，出事了算谁的——这部分不外包。

规矩三条：结论带证据；只读的随便跑，写入的先问我；同一个坑不踩第二次，踩了就写进笔记。

工具箱
